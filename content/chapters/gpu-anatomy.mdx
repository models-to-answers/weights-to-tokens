## Why the GPU is built differently

A CPU devotes substantial silicon to sophisticated control, large caches, and
fast execution of a small number of threads. A GPU accepts more latency per
thread and devotes far more of its area to parallel arithmetic. That trade only
pays when the workload exposes enough independent, regular work.

## A hierarchy built for throughput

High-bandwidth memory holds weights, KV-cache blocks, and working tensors. Cache
and memory controllers feed many streaming multiprocessors, usually called SMs.

An SM contains warp schedulers, execution pipelines, registers, and shared
memory. Many warps can remain resident so the scheduler has other eligible work
when one warp waits on a dependency or memory.

Two hierarchies meet inside the GPU. The hardware hierarchy is GPU → SM →
scheduler → execution and memory pipelines. The work hierarchy is kernel grid
→ block → threads → warps. Hardware admits a complete block to one SM, groups
its threads into warps, and lets a scheduler choose eligible warps for
instruction issue. Blocks and warps are assigned work, not permanent physical
layers.

Exact unit counts vary by GPU generation. The durable mental model is how the
work hierarchy maps onto the hardware hierarchy.

### Resources determine residency

An SM admits whole blocks only when it has enough registers, shared memory,
thread slots, warp slots, and block slots. The first exhausted resource limits
how many blocks and warps can be resident. Resident does not mean eligible:
scoreboard dependencies, barriers, memory waits, and unavailable pipelines can
still prevent issue.

Ordinary arithmetic, tensor operations, integer/address work, special
functions, and loads/stores route to different execution pipelines. Results
normally write back to registers; memory operations continue through the
on-chip hierarchy toward L2 and HBM.
